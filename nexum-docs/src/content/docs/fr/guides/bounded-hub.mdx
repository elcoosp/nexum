Par défaut, la file du hub nexum est non bornée : les producteurs ne bloquent jamais et les événements ne sont jamais abandonnés. Lorsque votre consommateur peut être lent — un thread d'UI sous charge, un appel réseau dans le pipeline — un hub **borné** vous donne une contre-pression explicite au lieu d'une croissance mémoire non bornée.

## Créer et installer un hub borné

Construisez le hub vous-même et installez-le avec `init_with`, qui renvoie le handle consommateur associé :

<Code lang="rust" code={`use nexum::platform::init_with;
use nexum_core::{Config, DeepLinkHub};

let config = Config::builder().scheme("myapp").build().expect("valid config");

let hub = DeepLinkHub::bounded(16);
let handle = init_with(&config, hub).expect("deep-link init");`} />

`init_with` installe le hub comme hub global au processus et exécute l'enregistrement OS habituel, donc tout ce qui est en aval — relais de plateforme, ponts d'adaptateur, `push_url` — alimente la file bornée.

## Comportement des push

| Méthode | Quand la file est pleine (natif) | Sur wasm |
| --- | --- | --- |
| `push_url`, `push_launch_url`, `push_event` | Bloque jusqu'à ce qu'un emplacement se libère | Abandonne l'événement (non bloquant) |
| `try_push_url`, `try_push_launch_url`, `try_push_event` | Renvoie immédiatement `Err(Error::QueueFull)` | Idem |

La capacité est ramenée à au moins un emplacement : `DeepLinkHub::bounded(0)` se comporte comme une file à un seul emplacement. `hub.capacity()` rapporte la limite effective (`None` pour les hubs non bornés).

Le comportement suivant est vérifié par les propres tests de la crate :

<Code lang="rust" code={`let hub = DeepLinkHub::bounded(2);
let handle = hub.handle();

hub.try_push_url("myapp://1").expect("room for 1");
hub.try_push_launch_url("myapp://2").expect("room for 2");
assert!(matches!(
    hub.try_push_url("myapp://3"),
    Err(nexum_core::Error::QueueFull)
));

// Vider un événement libère la place pour exactement un de plus.
handle.recv_event_blocking().expect("event");
hub.try_push_url("myapp://3").expect("room again");`} />

## Choisir une capacité

Choisissez la borne à partir de l'intervalle de vidage dans le pire cas de votre consommateur : un adaptateur d'UI qui se réveille par événement veut typiquement une petite borne (8–32) afin qu'une UI gelée arrête vite le producteur, tandis qu'un worker par lots qui vide avec `drain_events` peut se permettre une borne plus grande. Parce que les producteurs *bloquent* quand la file est pleine sur les cibles natives, une borne surdimensionnée ne coûte que de la mémoire, tandis qu'une borne sous-dimensionnée ajoute une contre-pression que vous devez observer dans les tests.

<Aside type="tip">
Pour une sémantique fire-and-forget sur les cibles natives, gardez le hub non borné par défaut ; le mode borné existe pour rendre la surcharge *observable*, pas pour la contourner.
</Aside>
